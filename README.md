# Harness Skills

Model-agnostic AI coding skills for the [Harness.io](https://harness.io) CI/CD platform. Generate pipeline YAML, manage resources, debug failures, analyze costs, and more from natural language.

This repository is designed as a workflow system, not just a folder of prompts. The top-level instructions (`AGENTS.md`, with `CLAUDE.md` importing it for Claude Code, plus `.cursor/rules/harness.mdc` and `.github/copilot-instructions.md`) establish shared behavior when you work from a clone, while individual skills specialize in creation, debugging, governance, and reporting tasks. Plugin installs ship those instruction files but do not load them; see [Install as a Claude Code Plugin](#install-as-a-claude-code-plugin).

## Prerequisites

- [Harness MCP v2 Server](https://github.com/harness/mcp-server) - required for MCP-powered skills. Most skills in this repo depend on it for Harness API access. It is not bundled with any plugin; see [MCP Setup](#mcp-setup).

## Install as a Claude Code Plugin

Each category is its own plugin. On Claude Code 2.1.275 or later, install one in a single step (swap `harness-fme` for any plugin in the tables above; each table shows its own install line):

```
/plugin install harness-fme --marketplace harness/harness-skills
```

On older versions, add the marketplace first, then install:

```
/plugin marketplace add harness/harness-skills
/plugin install harness-fme@harness-skills
```

The same from a shell:

```bash
claude plugin install harness-fme --marketplace harness/harness-skills

# older versions: add the marketplace first
claude plugin marketplace add harness/harness-skills
claude plugin install harness-fme@harness-skills
```

Invoke an installed skill as `/<plugin>:<skill>`:

```
/harness-fme:explain-flag
Explain the new_checkout flag in production
```

To update, run `/plugin marketplace update harness-skills`. Plugins are versioned by git commit. Each installed plugin caches a full copy of this repository (about 8 MB), because skills link to the shared `references/` and `templates/` at the repo root. Installing all nine plugins stores nine copies.

**Known gap:** plugin installs do not load the repo-level `AGENTS.md` rules (scope establishment, dependency checks, schema validation). FME skills load their shared rules through `references/fme/`; other skills rely on their own instructions. To get the repo-level rules, work from a clone (see [Quick Start without a plugin](#quick-start-without-a-plugin)).

## Install as a Cursor Plugin

Cursor installs the whole repository as one plugin, `harness-skills`, containing every skill in the tables above. Invoke a skill as `/<skill>`, for example `/explain-flag`.

- **Team and Enterprise:** in the Cursor dashboard, open Plugins & MCPs, choose Add Marketplace, and import the GitHub repository `harness/harness-skills`.
- **Local install:** clone into Cursor's local plugin folder:

  ```bash
  git clone https://github.com/harness/harness-skills.git ~/.cursor/plugins/local/harness-skills
  ```

- **Public marketplace:** a listing in the public Cursor marketplace requires a submission at cursor.com/marketplace/publish. That has not been done yet.

Cursor reads `.cursor-plugin/marketplace.json` before `.claude-plugin/marketplace.json`, so it sees the single `harness-skills` plugin rather than the nine Claude Code plugins.

## Install as a Codex Plugin

Codex also installs the whole repository as one plugin, `harness-skills`:

```bash
codex plugin marketplace add harness/harness-skills
codex
```

In Codex, open `/plugins`, install `harness-skills`, and start a new session.

To enable it for one repository only, add this to `.codex/config.toml` in that repository:

```toml
[plugins."harness-skills@harness-skills"]
enabled = true
```

Codex refreshes an installed plugin only when its version changes. The version is `version` in `skills/categories.json`, so Codex users do not see new skill content until that version is bumped.

## Quick Start without a plugin

Clone the repository to use the skills, the shared playbooks, and the repo-level rules together in any coding agent:

```bash
git clone https://github.com/harness/harness-skills.git
```

### FME with CLI or MCP (any coding agent)

1. Keep the repository's `skills/`, shared `references/`, and `templates/` available together. Load `AGENTS.md` and the selected skill; referencing just its SKILL.md without the linked playbooks is insufficient.
2. Choose the transport available to your agent: a preconfigured Harness CLI with shell access, or the [Harness MCP server](https://github.com/harness/mcp-server). Confirm the account, organization, project and intended environments without exposing credentials. CLI-only FME sessions do not require MCP; authentication should use the tool's supported secure setup outside the prompt.
3. Read the [FME tool map](references/fme/tool-map.md#transport-preflight-and-handoffs) and check capabilities for the installed version. It documents unsupported operations; CLI/MCP support is not identical. Segment key operations require MCP; some experiment updates also require MCP.
4. Use the skill file as instructions even if the host has no slash-skill invocation. Load linked skills explicitly during handoffs. Code-editing workflows also need the application repository and its test tools; live verification additionally needs an authorized running application.

The MCP examples in [MCP Setup](#mcp-setup) apply to MCP-powered sessions, not as a prerequisite for every FME workflow. See the [MCP setup playbook](references/mcp-setup.md) for connection, authentication, and read-only verification guidance.

## MCP Setup

The Harness MCP server is not bundled with any plugin; configure it for each tool you use. The examples run the server locally with `npx`. Never commit a real API key: use an environment reference or a placeholder like `<your-api-key>`. See the [MCP setup playbook](references/mcp-setup.md) for hosted vs. local servers, authentication, and read-only verification.

### Claude Code

Add a `.mcp.json` at the root of your own project (not this repo's root). Claude Code expands `${VAR}` from your environment, so the key stays out of the file:

```json
{
  "mcpServers": {
    "harness-mcp-v2": {
      "command": "npx",
      "args": ["-y", "harness-mcp-v2"],
      "env": {
        "HARNESS_API_KEY": "${HARNESS_API_KEY}"
      }
    }
  }
}
```

`claude mcp add --scope project` writes the same file (see `claude mcp add --help`). An `mcpServers` entry in `~/.claude/settings.json` is not read as MCP configuration.

### Cursor

Add to `~/.cursor/mcp.json` (user-level) or `.cursor/mcp.json` (project-level):

```json
{
  "mcpServers": {
    "harness-mcp-v2": {
      "command": "npx",
      "args": ["-y", "harness-mcp-v2"],
      "env": {
        "HARNESS_API_KEY": "<your-api-key>"
      }
    }
  }
}
```

### OpenAI Codex

Codex reads MCP servers from `~/.codex/config.toml` as TOML tables, not JSON. `env_vars` forwards the named variables from your shell environment:

```toml
[mcp_servers.harness-mcp-v2]
command = "npx"
args = ["-y", "harness-mcp-v2"]
env_vars = ["HARNESS_API_KEY"]
```

### VS Code (GitHub Copilot)

Add to `.vscode/mcp.json` in the workspace. This file is usually committed, so do not put a real key in it:

## Operating Model

The best Harness skills follow the same control flow even when they target different resource types:

1. **Establish scope first** - confirm account/org/project context before listing, creating, updating, or deleting resources.
2. **Verify dependencies before generating dependents** - do not reference connectors, secrets, environments, infrastructure, or templates that have not been confirmed to exist.
3. **Discover schema before writing payloads** - use MCP `harness_describe` or the installed CLI command specification and documented payload schema; stop when required capabilities are unavailable rather than guessing fields.

These repo-level playbooks live in:

- [`references/scope-establishment.md`](references/scope-establishment.md)
- [`references/dependency-check-playbook.md`](references/dependency-check-playbook.md)
- [`references/schema-validation-loop.md`](references/schema-validation-loop.md)
- [`templates/operation-summary.md`](templates/operation-summary.md)

## Workflow Modes

| Workflow mode | Representative skills | Use when |
|---------------|-----------------------|----------|
| Create and scaffold | `/create-pipeline`, `/create-service`, `/create-connector`, `/create-template`, `/fme-pipeline` | You need to define or generate new Harness resources and their YAML or MCP payloads. |
| Run and debug | `/run-pipeline`, `/debug-pipeline`, `/migrate-pipeline`, `/manage-delegates` | You already have resources and need to execute, diagnose, or repair behavior. |

## End-to-End Workflows

### New microservice setup

Use these skills in order:

1. `/create-connector`
2. `/create-secret`
3. `/create-service`
4. `/create-environment`
5. `/create-infrastructure`
6. `/create-pipeline`
7. `/create-trigger`

### Debug a failed deployment

Typical sequence:

1. `/run-pipeline` to identify the latest execution or reproduce the issue
2. `/debug-pipeline` to classify the failure and inspect root cause
3. `/template-usage` if shared templates may have propagated the issue
4. `/manage-delegates` if the failure points to delegate capacity or connectivity

## Migrating from the Flat Layout

Skills moved from `skills/<skill>/` to `skills/<category>/<skill>/`; the categories are listed in `skills/categories.json`. Old deep links and `@harness-skills/skills/<skill>/SKILL.md` references need the category segment:

```
Before: @harness-skills/skills/<skill>/SKILL.md
After:  @harness-skills/skills/<category>/<skill>/SKILL.md
Example: @harness-skills/skills/pipelines/create-pipeline/SKILL.md
```

Branches opened before the move: merge or rebase `main`, run `python3 scripts/migrate_to_categories.py --repair` (add `--map <new-skill>=<category>` for each skill the script does not know, repeatable), review the changes, and commit. The script is temporary and will be removed after the merge window.

If you installed with `npx skills add`, re-run your install to pick up the new layout.

## Shared Playbooks and Templates

Use root-level shared assets for behavior that should stay consistent across many skills:

- `references/` - reusable operating guidance such as scope establishment, dependency verification, and schema-validation loops
- `templates/` - reusable output contracts such as operation summaries and report formats

Use per-skill `references/` or `templates/` when the content is domain-specific and should not be imported broadly.

## Skill Anatomy

Each skill is a directory at `skills/<category>/<skill>/` containing a `SKILL.md` with YAML frontmatter and a consistent markdown body: `# Title`, `## Instructions`, `## Examples`, `## Performance Notes`, and `## Troubleshooting`. Start from [`template/SKILL.md.template`](template/SKILL.md.template); [CONTRIBUTING.md](CONTRIBUTING.md) documents the frontmatter fields, description rules, and shared-reference conventions.

For complex skills, add `references/` or `templates/` under the skill directory rather than bloating `SKILL.md`.

## MCP Tools

MCP-powered skills use the [Harness MCP v2 server](https://github.com/harness/mcp-server), which provides 10 generic tools dispatched by `resource_type`:

| Tool | Purpose |
|------|---------|
| `harness_list` | List resources |
| `harness_get` | Get resource details |
| `harness_create` | Create a resource |
| `harness_update` | Update a resource |
| `harness_delete` | Delete a resource |
| `harness_execute` | Execute an action |
| `harness_search` | Search across resources |
| `harness_describe` | Get resource schema |
| `harness_diagnose` | Diagnose issues |
| `harness_status` | Check system status |
